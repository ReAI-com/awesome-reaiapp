## 一、AI 员工是什么

AI 员工是辅助人的岗位工作台。人操作时，它辅助人完成岗位工作；自主运行时，它本身就是一个 AI 员工。

公司可以看成一张 IPO（Input-Process-Output）网络。每个岗位是一个小 IPO：接收原始输入，按岗位规则加工，产出规范数据、交付物或检查结论，再交给下游岗位。

| 记号 | 含义 | 例 |
| --- | --- | --- |
| A | 原始事实：上传、抓取或回传的原件，只增不改 | 银行流水、简历、用户反馈 |
| B | 规范数据：A 按岗位规则清洗后的结构化记录，可修订、带版本 | 凭证分录、员工档案、需求池 |
| C | 交付物：按需求从 B 筛选加工生成，由人从候选中选定并签字 | 报价单、设计稿、PRD |
| D | 规则体系：对 A、B（含他人数据与物理世界回传）执行的检查 | 发票合规、进度检查、品牌规范校验 |

## 二、三种范式

| 范式 | 流转 | 价值 | 看板主形态 |
| --- | --- | --- | --- |
| A-B 解释型 | 原始事实 A → 岗位清洗工作流 → 规范数据 B；Agent 基于 B 解释 | 对 B 的解释权 | B 看板（指标 / 表 / 图 / 文档） |
| A-B-C 创作型 | A → B → 按需求筛选加工生成交付物 C；C 可回流成新的 B | 品味；人从候选中选定并签字 | C 交付台（多候选、选定、导出、回流） |
| A-B-D 检查型 | A、B（含他人数据 / 物理世界回传）→ 规则体系 D → 检查结果 | 刚性规范，协助企业网络运作 | D 验收台（规则版本、检查运行、问题升级给人） |

一个岗位有一个主范式，可以叠加组合范式，例如财务以 A-B 为主、叠加 D。

### 不变量

- A 只增不改。
- 每条 B 都有明确来源（导入 / 人工 / 回流，见 6.2）。历史数据来源未知时如实标注，不补造。
- 工作流发布即快照，改动发新版本。
- 事实、推测、过程分开存放。
- C 由人选定，并绑定具体候选版本。
- D 的规则定义与检查运行分离；运行冻结输入版本，结论可复核。

## 三、看板 = 主题最小功能界面

同一岗位的多个看板，是围绕不同主题的「最小功能界面」。每个看板相当于一个小型网页 App，例如财务的「收支」「发票核对」「凭证待办」各是一个看板。看板不是同一份数据的不同视图标签：

- 有主题名、图标和一句用途说明；
- 声明自己读哪些 B（及他人 B / 物理回传），产出什么（无 / C / D 结果）；
- 由声明式组件拼装（见第七节），因此可以由 Agent 按自然语言生成，用户确认后加入导航；
- 范式类型（B / C / D）是看板的属性，不是导航的固定分组。界面上只在开发者视角用徽标标出；普通员工只看到图标与名称，用途在悬停提示里。

导航按「岗位 → 主题看板列表」组织。每个岗位默认带 3–4 个主题看板，覆盖其主范式与组合范式。

### 界面呈现与权限视角（v2.1）

产品面向普通员工：A / B / C / D 记号、范式代码、版本号、ID、指纹、字段键名、动作 ID 与工作流原理只在「开发者」视角出现，合同行为不变，只是不再常驻展示。错误、进度、检查结果与示例数据同时提供人话说法，其他视角包括错误路径都只显示人话。设计稿外壳提供四档权限视角（员工 / 部门负责人 / 管理员 / 开发者），只影响可见范围：切换视角不关闭仍可访问的业务抽屉，不丢未保存的草稿，也不撤回在途保存；只有切出开发者视角时，开发者专属的抽屉随之关闭。

- 员工：工作台、主题看板、Agent；资料只看划给自己的部分和公司公开资料（只读）；公司流程只看自己与直接上下游；设置只含通知、显示与「我的 Agent」。
- 部门负责人：另可看本部门资料、本部门流程全貌、部门成员与分工（只读）。
- 管理员：另可看全部资料、全公司流程，可编辑公司设置（公司名称、金额显示），成员权限在演示中只读。本部门资料、全部资料读取各岗位的实时资料状态，只读。
- 开发者：另可看岗位范式开发模式、工作流页（调试与运行记录）、诊断信息与全部技术字段。

资料上传或回流后自动整理，结果以「已整理 N 条 / 有 N 处需要你确认」出现在资料行内，经人「去确认」后整批入库。交付生成与检查保持现有触发方式，仍由看板上的按钮发起。说明性长文本收进 (i) 悬停提示，不常用操作收进「更多」菜单；菜单是独立浮层，空间不足时向上展开。

设置分两层。公司名称与金额显示单位是公司级共享配置：全部岗位共用一份，演示中只有管理员视角可以编辑，保存后所有岗位立即生效。通知、显示等岗位相关设置按岗位实例保存，与一岗一实例的岗位配置一致。编辑公司设置时的草稿与保存操作仍按岗位实例隔离，切换岗位后迟到的保存结果会被忽略。

## 五、复用而非重造

v2 不自建云存储、工作流引擎、Agent 运行时或编排网络，而是复用已有机制。表中外脑、JOJO 网络与 ROMP 的「已上线」来自外脑侧文档，本次未核验部署状态。

| 机制 | 复用对象 | 现状 | 设计稿呈现 |
| --- | --- | --- | --- |
| 数据获取 A：上传 | v1 原件存储（SHA-256 去重、只增不改） | 已实现（本地） | 上传区、原件列表、指纹、被哪些 B 引用 |
| 数据获取 A：云端存储 | 外脑文件存储（内容哈希去重，OAuth `project:files:write`） | 外脑侧已上线；Host 侧无对应插件通道 | 数据源卡片标「待接入」 |
| 数据获取 A：数据源 / Agent 抓取 | v1 `SourceAdapter` 合同 | 合同已有，无真实采集器 | 邮箱 / 网盘 / API 卡片标「未实现」 |
| 清洗 A→B、生成 B→C、规则 D | 外脑工作流（Markdown 流程 → 发布快照 → 运行日志），插件经 `ctx.flowApi`（`cloud.workflow.invoke@1`）调用 | 外脑侧已上线。插件侧缺口：`flowApi` 只接收 Host 登记的逻辑工作流名，无快照目录、精确版本选择和历史运行日志查询；`wait_for_input` 不可用；当前稳定返回 `FLOW_SCOPE_UNAVAILABLE`（不重试、不绕通道） | 工作流页分两区：「本地规则（演示）」可运行并有本地运行记录；「外脑工作流」显示逻辑名、期望快照与「未开通」状态 |
| Agent 入口 | [Agent Service v2](agent-service-v2.md)（`ctx.agent`，Pi / DSH / Codex，省略 runtime 时用 Host 默认） | 需平台批准 `agent.session@2` 与 `cloud.model.invoke@1` | 右侧非模态 Agent 面板；未批准时标「演示分析」 |
| Agent 消息模型 | ni-chat 消息规范（ROMP 的客户端模型）：消息由 parts 组成（text / thinking / tool_call / tool_result / file / image / context_ref / interaction_ref），瞬时状态 typing / thinking / tool_calling，需人回答的 Interaction（choice / text，pending → answered / cancelled / expired） | ni-chat 界面组件是官方插件内部素材，不直接依赖其包；ROMP 第三方 OAuth 暂不可用 | 思考与工具步骤折叠显示；看板提案、C 选定签字、D 问题升级用 Interaction 卡片，回答后状态不回退 |
| IPO 网络 | JOJO 项目网络：`NetworkGraph { nodes, edges, entries }`；点只管 I/O，边订阅并投递，入口来源为 subscription / romp / api | 编辑、手动运行、停止已上线；ROMP / 订阅入口真实接线未完成；无权重字段 | 「公司流程」页沿用点 / 边 / 入口语义与视觉，只展示，不调度、不编辑；员工只看自己与直接上下游，部门负责人看本部门，管理员看全公司，边绑定的工作流只在开发者视角可见 |
| ROMP 字段 | ROMP Message：`sender`、`origin`、`parts[]`、`reply_to`、`metadata`；tool_call 状态 pending / running / done / error；typing 状态 thinking / typing / tool_calling / idle | 外脑侧已上线 | Agent 面板字段按 ROMP 命名；网络位置（岗位、看板、边）放 `metadata` |
| 交付物导出（PPT / Word / Excel / 设计稿） | 平台已有文档类能力 | 具体接口第二阶段核实 | C 交付台导出按钮标格式与「待接入」 |

两条约定：

- **AI 员工 Agent 消息 = ni-chat 消息子集**。将来经 ROMP 接入同一岗位 Agent 时，不需要换消息模型。
- **AI 员工网络 = JOJO 网络的岗位级投影**。岗位间流转将来落成 JOJO 边，不在插件内自建编排。

## 六、最小合同

以下合同在第一阶段冻结。设计稿的每个交互都应能对应到其中一条；第二阶段实现以本节为准。

### 6.1 A→B 流程（沿用 v1）

保存 A（只增不改、指纹去重）→ 触发整理（手动或自动）→ 复核问题 → 发布 B → 人工更正产生新版本。

- 整理结果含无效行时，整批不发布部分记录，问题列表供人处理。
- 更正时校验期望版本；冲突提示「已被他人修改，请刷新后重试」。
- PDF、图片、办公文档只保存原件，界面明确提示「暂不支持自动整理」。

### 6.2 B 的来源

| 来源 | 必带字段 | 说明 |
| --- | --- | --- |
| 导入 | A 指纹 + 整理规则 / 工作流引用（本地规则 ID，或外脑逻辑名 + 回执版本） | 常规路径 |
| 人工 | 操作者 + 时间 | v1 已支持的人工创建 |
| 回流 | 选定的 C 候选版本 ID | 回流时把该 C 版本的**规范内容字节快照**（候选本身的结构化 / 文本内容，不是 PPT / Word 等格式导出）另存为一份新 A，来源类型 `derived`，记录候选版本引用与指纹，再走导入。不依赖格式导出服务，保证任何 B 都能顺链追到 A |
| 历史未知 | `unknown` | 旧数据如实标注，不补造工作流版本 |

### 6.3 C 与 D 的复核

**C（交付）**

- 流程：交付任务 → 候选 → 选定 → 签字。每个候选有版本 ID 和生成时的输入 B 版本集合；选定记录选定者、时间、候选版本 ID。
- 签字回执 = `{签字者, 时间, 候选版本 ID, 输入 B 版本集合, 幂等键}`。同幂等键同内容重复提交返回原回执；同键不同内容拒绝。
- 输入 B 变化后，旧签字保留，标「输入已更新，签字基于旧版本」，可重新生成。不自动作废，不静默沿用。

**D（检查）**

- 规则定义（规则 ID + 版本；检查对象为本岗 B、他人 B 引用或物理回传）与检查运行（运行 ID、规则版本、冻结的输入快照引用、证据）分离。
- 结果三分：业务未通过 / 检查运行失败 / 证据不足。
- 规则或输入更新后，旧结论标「已过期，需重新检查」。

### 6.4 看板的动作边界

- 看板定义 = 组件参数 + 数据绑定 + **可信动作白名单引用**。
- 白名单由插件代码提供，例如 `open-record`、`select-candidate`、`sign-candidate`、`run-check`、`escalate-issue`、`reflow-to-b`。组件只能引用白名单内动作，不能写脚本、事件或任意写入。
- 开发模式只能查看白名单，并为本看板勾选启用子集；不能新增动作、修改实现或扩大权限。执行时仍检查当前权限，密码解锁不替代授权。
- Agent 提案只能引用已有动作。提案预览只读，动作按钮禁用并注明「确认添加后可用」。
- 业务提交时独立校验：动作是否在白名单、对象版本是否匹配、是否需要用户确认。
- 设计稿包含三个反例：提案引用未知字段、引用不存在的动作、提案已过期（岗位配置版本变化），分别展示拒绝原因。

### 6.5 岗位、实例与跨岗读取

- **演示外壳切岗**：只是设计稿里切换示例配置，不代表产品行为。
- **真实产品**：一个岗位 = 一个插件实例（独立 `appId`，沿用 v1 生成器）。IPO 节点点击 = 打开该岗位插件，未安装则提示；不在同一实例里切岗。
- **跨岗读取**：引用格式 `{appId, role, objectType, objectId, version}`。需对方授权，节点跳转不扩大读取权限。第一阶段只定义引用格式与「未授权 / 未安装」呈现，不定义授权机制（见第九节）。
- 切换岗位或实例时，草稿、Agent 消息与待确认操作各自隔离；旧任务的迟到结果忽略。
- 开发者密码只防误改配置，不是岗位访问权限。

### 6.6 Agent 消息与 ni-chat / ROMP 映射

| 呈现 | ni-chat / ROMP 字段 | 当前真实可得（Agent Service v2） | 设计稿处理 |
| --- | --- | --- | --- |
| 正文 | `text` | 有（结果正文为文本，buffered 交付） | 正常显示 |
| 思考摘要 | `thinking` | 无 | 不补造，仅标注「未来接入」 |
| 工具步骤 | `tool_call` / `tool_result` | 以 v2 事件为准，不保证 | 有事件才显示；演示模式标「演示」 |
| 引用卡片（A/B/C/D 对象） | `webpage` 形态卡片 + `metadata` 中的对象引用 | 插件本地生成 | 点击在左侧打开对象 |
| 待人确认 | `Interaction`（choice / text） | 插件本地状态；ni-chat 的 Interaction 不是公共服务 | 「已回答」与「提交成功 / 冲突 / 失败」分两步显示 |
| 上下文标记 | `context_ref` | ni-chat Mock 扩展 | 演示专用，标注 |

状态名映射：

| ni-chat | ROMP |
| --- | --- |
| `completed` | `done` |
| `failed` | `error` |

业务选择卡不得代替 Host 授权入口，权限请求仍走 Host。

### 6.7 Agent 配置的事实源

| 层级 | 事实源 | 说明 |
| --- | --- | --- |
| 岗位默认值 | 插件 Manifest `contributes.agentFeatures`（Host API ≥ 1.23） | 只声明少量稳定功能，建议 4 个：`analyze`（基于 B 解释）、`propose-board`（看板提案）、`generate-c`（生成交付候选）、`explain-d`（解释检查结果）。每项含提示词模板、参数槽、工具基集、可选引擎锁定 |
| 用户覆盖 | Host「设置 › 插件 Agent 配置」页（`system.tasks@1` 的 `agent-config` 入口） | 插件不另建第二套提示词 / 引擎编辑器 |
| 任务参数 | 创建会话时的 `featureRef` + `featureParams` | 按 `backends().capabilities.configuration.featureRef` 探测后附带 |

- 所有看板复用这几项功能，看板上下文经已声明的参数槽或任务正文传入。**新增看板不修改 Manifest、不增加功能项、不增加权限**；功能项是安装包静态声明，每插件上限 16。
- 插件设置页「Agent」区只显示实际生效配置与来源（默认 / 用户覆盖），以及「在 Host 中修改」跳转。配置变更对新会话生效。
- 开发模式保留岗位范式（字段、整理规则、看板默认值），不再包含提示词 / Skill / 引擎编辑。

### 6.8 错误类型与恢复动作

| 类型 | 例 | 呈现 | 恢复动作 |
| --- | --- | --- | --- |
| 可重试（未受理） | 提交前网络失败、服务暂不可用 | 原因 + 重试 | 用同一幂等键重试 |
| 等待超时（已受理） | 已取得受理回执（如 Agent v2 `{sessionId, turnId}`），等待结果超时 | 「已提交，结果未返回」 | 按回执中的服务任务 ID 继续查询，不重新发起 |
| 回执丢失（受理未知） | 提交后未拿到受理回执，无服务任务 ID | 「提交结果未知，正在确认」 | 用原会话、原幂等键、完整原请求再次提交（Agent v2 即再次 `startTurn`），取回原回执后再查询；不创建新键 |
| 未开通 / 未批准 | `FLOW_SCOPE_UNAVAILABLE`、能力未获平台批准 | 说明当前不可用及原因 | 无重试；切到本地演示或查看说明 |
| 无权限 | 用户未授予 | 缺哪个权限 | 引导「已安装 → 权限」 |
| 余额不足 | `AI_PAYMENT_REQUIRED` | 额度不足 | 补充额度说明，无重试 |
| 冲突 | 版本不匹配 | 已被修改 | 刷新后重试 |
| 业务拒绝 | 提案越权、对象过期 | 具体原因 | 重新生成 |

回执丢失的处理依据 [Agent Service v2](agent-service-v2.md)「提交、等待与重试」一节。

错误码、版本等诊断信息只在「Host 开发者模式」下可展开。设计稿外壳用「开发者」权限视角模拟该模式，切到其他视角立即收起。岗位密码解锁不等于 Host 开发者模式。

## 七、看板组件库与可信动作

组件库是声明式的，供看板调整界面与后续 AI 员工功能库复用。在 v1 绑定类型（`count` / `sum` / `distinct` / `difference` / `records` / `reports`）之上新增展示组件。每个组件定义参数、数据绑定和可引用的可信动作，第二阶段落成正式合同。

| 组件 | 用途 | 可引用动作 |
| --- | --- | --- |
| `metric` | 指标卡 | 第二阶段确定 |
| `trend` | 趋势图 | 第二阶段确定 |
| `breakdown` | 分组条形 | 第二阶段确定 |
| `records` | 记录表 | 第二阶段确定 |
| `kanban` | 状态列，按 B 的枚举字段分列 | 第二阶段确定 |
| `deliverable` | C 候选卡组 | `select-candidate`、`sign-candidate`、`reflow-to-b` |
| `checklist` | D 检查结果 | `run-check`、`escalate-issue` |
| `timeline` | 督办 / 里程碑 | 第二阶段确定 |

看板调整流程：用户用自然语言描述想要的看板 → Agent 输出声明式提案（布局 + 对 B 的数据绑定 + 动作引用）→ 只读预览 → 用户确认后加入导航。提案不执行脚本、不改数据，动作边界按 6.4。重复确认同一提案是幂等操作（沿用 v1）。

## 八、与 v1 的差异

| 方面 | v1（`0.2.0` 源码） | v2 |
| --- | --- | --- |
| 范式 | 原始资料 → 标准记录 → 岗位 Agent（相当于 A-B） | A-B / A-B-C / A-B-D 三种，可组合 |

| 开发模式 | 可编辑提示词、inline Skill、SOP、HTML / CSS | 只编辑岗位范式（字段、整理规则、看板默认值、可信动作子集）；提示词与引擎由 Host 插件 Agent 配置页管理 |
| 交付与检查 | 报告草稿 | 新增 C（候选、选定、签字回执、回流）与 D（规则版本、检查运行、结论过期） |

v1 的原件、记录版本、页面提案确认与幂等、岗位隔离等合同继续有效。

## 九、开放问题

第二阶段开工前需与平台确认：

1. **跨岗授权机制**：读取他人 B 时由谁授权、授权粒度和撤销方式。
2. **逻辑工作流名 → 不可变快照映射**：插件如何得知逻辑名对应的快照版本，回执如何证明本次运行使用的版本，以及如何获取运行日志。
3. **Agent 过程事件**：Agent Service v2 是否稳定提供思考摘要与工具步骤事件。
4. **交付物格式导出接口**：PPT / Word / Excel / 设计稿导出使用哪项平台能力及其权限。
5. **IPO 网络落成 JOJO 边**：岗位间流转如何映射为 JOJO 网络的边与入口，以及岗位插件与网络节点的身份对应关系。
