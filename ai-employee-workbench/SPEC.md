# AI 员工工作台 3.0

状态：3.0 本地实现已完成。验证方式和当前边界见 README；真实模型质量验收需使用用户配置的模型。

## 已确认的产品边界

- 3.0 是本次全新开发的版本，不存在另一份需要沿用的 3.0 设计。
- 独立本地 Web 项目，代码、依赖、启动方式和数据存储自成一体。
- 当前仓库中的文档和 HTML 仅作为业务与交互参考，不复用现有插件、Host 或 JOJO 的实现。按后续确认的上线要求，HTTPS 部署接入外脑 OAuth 身份验证与模型网关；本地独立模式仍支持自行配置模型。
- 本项目全部内容放在 `ai-employee-workbench/`；用户数据与凭据不进入源码。
- 用户指定工作目录，项目可读取该目录；上传文件保存到所属工作目录。
- 支持多个清洗规范：提示词、结构化数据 Schema、路由逻辑和工作流；Schema 由 Agent 辅助自动生成。
- 管理员可用传统数据库表格界面查看 B；普通用户可生成和使用主题看板，并向岗位专家提问。
- 动态看板是独立 WebApp，通过 REST API 获取 B 的 Schema、读取数据及执行允许的操作。
- 三类 Agent 均有独立配置：模型、参数、协议、提示词、tools、MCP、skills、harness。首版 harness 使用 Pi。

## A-B-C/D 业务规则

| 对象 | 定义与约束 |
| --- | --- |
| A 原始资料 | 保存原始文件字节、指纹和来源。已有原件不覆盖；同一个逻辑文件发生更新时，新增原件版本。 |
| B 结构化数据 | 由清洗规范生成，有 Schema、版本、来源 A 和对应清洗运行记录。修订保留历史。 |
| C 交付物 | 基于确定的 B 版本生成候选；记录人的选定与签字。输入更新后保留历史并标记过时。 |
| D 检查 | 分离规则版本与检查运行，冻结输入和证据，区分业务未通过、执行失败和证据不足。 |

看板是业务界面，不直接等同于 C。看板可展示 B、处理 C 或发起 D。

## Agent 分工

| Agent | 职责 | 应用必须核验的结果 |
| --- | --- | --- |
| 清洗 Agent-001 | 理解原始资料，选择匹配规范，生成或使用 Schema，按工作流清洗。 | Schema 与记录校验、来源关联、版本一致性、批次事务提交。 |
| 生成看板 Agent-002 | 按用户要求生成独立 WebApp，并通过 REST API 绑定当前岗位数据。 | 产物完整性、可预览性、API 范围和配置，确认后加入导航。 |
| 专家 Agent-003 | 查询当前岗位数据并回答用户，保留会话与可核对的数据引用。 | 数据范围、引用有效性、事实与推测的区分。 |

模型输出不直接改变完成状态。上传、任务调度、校验、事务提交及最终状态由本地后端控制。

## 文件状态与清洗生命周期

必须展示用户指定的九个业务标签：上传、上传中、上传完成、开始清洗、清洗中、清洗完成、有更新、更新中、更新完成。

- 上传进度与清洗进度来自真实操作，不通过计时器模拟完成。
- 上传完成只说明原件已持久化，不说明结构化数据已经可用。
- 清洗完成只在当前输入版本的 B 成功提交后出现。
- 发现更新时保留旧原件与已发布 B，新清洗成功后再切换当前数据版本。
- 上传或清洗失败、取消、中断时有明确反馈、运行记录与恢复入口，不能长期伪装为运行中。
- 重试应保持幂等；过期任务不能覆盖更新的文件或数据版本。
- 支持查看当前状态、状态历史、对应输入版本及失败原因。

实现采用文件主状态与任务执行状态两层。文件主状态保持业务标签，任务执行状态单独记录 `queued`、`running`、`waiting_review`、`succeeded`、`failed`、`cancelled`、`superseded`、`interrupted`。

| 文件主状态 | 进入条件 |
| --- | --- |
| 上传 | 上传任务已登记，尚未开始接收文件。 |
| 上传中 | 接收上传或复制目录文件，原件尚未完整持久化。 |
| 上传完成 | 原件完整写入并完成指纹校验。 |
| 开始清洗 | 已冻结原件、清洗规范和 Agent 配置版本，任务等待执行。 |
| 清洗中 | 正在路由、确定 Schema、提取、规范化、校验或等待复核。 |
| 清洗完成 | 首批结构化数据通过校验并成功发布。 |
| 有更新 | 原件或生效规范发生变化，已发布数据尚未更新。 |
| 更新中 | 正在处理新版本；旧版已发布数据继续可用。 |
| 更新完成 | 最新结构化数据成功发布，当前版本指针已切换。 |

失败或取消时保留主状态及失败阶段，同时明确显示任务异常；不能仅显示“清洗中”让用户误以为仍在执行。首次清洗前发生原件更新时，冻结新的原件版本重新排队，不假定已有 B。

文件监听提示可能的变化，内容哈希用于确认变化。扫描排除应用自身数据库、临时上传及快照目录，避免循环导入。外部原文件缺失不删除已保存的 A/B。

每个清洗任务绑定原件版本、规范版本、Agent 配置版本及任务代次。结果先保存为草稿，通过 Schema 校验后在一个事务中写入 B、来源关系及发布回执，再切换当前版本。发布前再次校验任务有效性，过期结果或人工修订冲突不能覆盖当前数据。

“已完成数据清洗”由当前原件和规范版本是否匹配已发布 B 推导，不提供脱离运行结果的成功勾选。更新期间看板和专家继续读取上一版已发布 B，并提示数据正在更新。

## 界面参考

- 左侧岗位及主题看板导航，中央业务区，右侧可同时操作的 Agent 面板。
- 上传和工作目录设置有清晰入口；管理员另有数据表、Schema、运行记录和 Agent 配置入口。
- 普通用户界面优先使用业务语言；技术字段与诊断信息按需展开。
- 岗位切换后，会话、草稿、看板和在途任务保持各自归属。

## 已确认的架构边界

首版为本机单用户，支持多个岗位工作区。管理员模式是数据和 Agent 配置入口，不是多人权限系统。工作区目录独占、不可重叠；数据库、会话、规范、看板和任务按工作区隔离。监听地址仅为本机回环地址，不提供多人账号及公司／客户／案件权限管理。

## 验收原则

- 用真实文件证明目录读取、上传持久化、更新发现与状态转换。
- 用真实清洗运行证明 A → B 的 Schema 校验、事务发布、可追溯和失败恢复。
- 验证管理员可读结构化数据，生成的 WebApp 可通过 REST API 获取最新数据。
- 验证三类 Agent 配置实际进入 Pi 运行，而非仅保存在表单。
- 区分本地规则或测试替身验证、真实模型验证和浏览器交互验证；缺少的证据明确标注。
- 本次授权为本地开发与相关验证，不包含远端推送、合并或生产发布。
